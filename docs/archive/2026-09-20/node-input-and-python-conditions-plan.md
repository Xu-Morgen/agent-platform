# 节点输入机制与 Python 条件块开发计划

日期：2026-09-20。状态：P1–P4 已完成实施及下列轻量验收。本文件归档保留原始要求、实施记录与验证边界。

本计划已完成，后续目标为[文档出题业务扩展](../../document-question-quality-plan.md)实施。需求来源为用户确认：简单模式自动携带上一节点的主输入与结果，高级模式允许选择完整参考输出；if 使用 Python 条件块决定分支。

## 1. 目标与当前差异

实施前普通节点只接收上一层完整输出；if.condition 引用此前执行的 bool 块，若该块紧邻 if，分支首节点收到的也是 bool。while 已有独立执行的 Python 条件块，但尚无统一的节点参考输入。

目标是“主数据顺序传递，参考数据完整引用，Python 判断控制路径”。模型只输出声明契约允许的数据，不生成 Python、流程、接线或实例。Python 条件由资源开发者编写为受信任的通用块，配置者在服务页选择；不增加任意表达式编辑器或 eval 入口。

不另建保留输入容器，不增加资源类别，不引入任意字段映射、全局可变上下文、历史执行位置回退、checkpointer 或失败任务恢复。

## 2. 统一节点输入

### 2.1 单一封装

业务包、通用块及条件块采用同一个节点输入概念：

```text
NodeInput[P, R] = {
  primary: P,
  references: R
}
```

P 是主数据契约，R 是固定位置的参考契约元组；JSON 表现为数组。节点输出仍是资源自己声明的业务结果，不强制添加封装。平台负责输入封装，业务字段的选取、改名、结构转换、状态合并由通用块完成。

服务调用输入和服务最终返回仍是业务契约，用户不填写 NodeInput。平台在进入首节点时封装；服务返回仍自动取顶层最后一步完整输出。API 请求与响应的业务契约独立保留，API 块接收 NodeInput 后通过代码构造请求，不把整份节点封装直接当作 HTTP 响应或请求契约。

### 2.2 简单模式（默认，不配置来源）

- primary：上一节点完整输出；服务第一步取完整服务输入。
- references：只有一项，为上一节点此次执行时的 primary；服务第一步为零项。
- 不递归收集上一节点的 references，不复制完整输入封装形成无限嵌套。
- 默认绑定不符合资源声明的参考数量或类型时阻止保存；不自动删减、补空值或转换类型。“不用配置”不等于无需声明契约。
- 平台保存此次调用的主输入副本和通过校验的输出；引用不允许下游原地修改上游数据。

例如“读取 → 出题 → 审题”：审题的 primary 是题目，默认 references[0] 是出题时的资料。在长链路中需要持续使用原文，应通过高级模式明确引用读取节点。

### 2.3 高级模式（替换默认参考列表）

primary 仍自动确定，不可改线。references 按顺序绑定完整来源，可配置空列表；显式配置替换默认列表，不暗中追加默认项。允许来源为完整服务输入、可见节点完整输出和当前循环携带值；业务包、通用块、控制容器均可作为合法节点来源。

每项只记录来源种类与节点 ID，不提供字段路径、表达式、重命名或拼装。资源声明每个参考位置的类型与说明，配置者选择对应来源。重复来源应明确提示并拒绝重复绑定，避免无意多次发送相同数据。

### 2.4 控制作用域与本次执行身份

| 场景 | 规则 |
| --- | --- |
| 同作用域此前节点、外层此前节点 | 可以引用；保存时确认必然可用 |
| 前向引用、自身、未执行兄弟分支 | 禁止引用 |
| 容器内部结果被外部引用 | 禁止穿透，只引用容器出口 |
| 循环内部节点 | 只引用当前轮此前执行的结果；不得读取上一轮残留结果 |
| 上一轮题目或最佳版本 | 显式存入 carry，不增加隐式历史节点索引 |
| if 条件及分支首节点 | primary 都是进入 if 的完整值；默认参考沿用进入 if 前的上一节点主输入，条件执行不成为业务前驱 |
| while 条件及循环体首节点 | primary 都是当前 carry，默认参考为空；需要原文或其他状态时显式配置高级引用 |
| repeat 循环体首节点 | 与 while 循环体相同 |
| 容器之后的普通节点 | primary 为容器完整输出；默认参考为容器本次入口主数据（循环为初始 carry），不是某个内部节点或条件 bool |

分支、循环体内第二步起按普通顺序规则处理。if 入口、循环初始值及更新值仍传递完整数据；零次 repeat 和首次条件为假的 while 直接返回初始 carry。静态校验和运行时解析必须共用相同的作用域规则。实现应以任务、容器路径、轮次及尝试身份隔离数据，禁止仅按全局 nodeId 取“最后一个结果”。

### 2.5 契约、Prompt 与校验责任

- 从资源声明的 P 和 R 推导完整入口类型、Schema 和编辑器表单，不维护第二份手写 Schema。复用原校验器，包含自定义 validator、严格标量、未知字段限制和固定数组位置约束。
- 简单模式也校验参考项。高级列表的数量、顺序、来源可见性和每项契约均在保存前校验，运行时再次校验实际值。
- Python 固定元组与 JSON 数组的转换应经统一序列化边界处理，不能为了转换关闭严格元素校验；列入边界验收。
- Prompt 使用明确的 primary/references 路径（目标形式如 input.primary、input.references[0]）；实际占位符语法和加载检查在 P1 一次确定。仅发送 Prompt 声明使用的数据，不自动把参考列表附加到模型消息。
- 目标资源的入口校验应在对应生产节点的输出检查阶段尽可能完成，维持“数据不合法，消费者不执行”的规则。主数据造成的错误按现有 retryLimit 重试直接生产节点；历史参考值缺失、参考错误和消费者跨字段校验错误不得通过重跑无关的上一节点来修复，应明确定位后失败。P1 明确错误分类并同步现有重试约定。

## 3. if / while 的 Python 条件

将 if.condition 从 PortReference 替换为 kind=block 的完整节点声明，与 while.condition 统一。条件块接收 NodeInput，读取 AI 输出中已声明的字段，用 Python 返回严格 bool；字符串、数字、对象形式的真假值均拒绝。

```text
进入 if 的业务数据 → Python 条件块 → bool
                 ├─ true：完整业务数据 → then 分支
                 └─ false：完整业务数据 → else 分支
```

条件块在一次判断尝试中独立执行，分支数据不被 bool 替换。两分支统一出口契约；空分支仍按明确的完整输出绑定校验。while 每次检查接收当前 carry，达到 maxIterations 后仍为真沿用 LOOP_ITERATION_LIMIT；退出循环不代表业务验收通过。

条件执行复用平台块调用、任务路径、错误记录、预算边界和取消检查。条件块不是包调用，不增加包 loop 计数；错误不得默认为 false。输出契约错误沿用明确的重试规则；不回滚外部操作。条件实现应只判断数据，不把业务 API 操作混入选择逻辑。

## 4. 协议、版本与编辑器

这次是破坏性协议更新，不维护旧裸输入调用模式、旧 if 引用模式或字段映射兼容分支。资源入口契约、包 Prompt 和资源版本需要同步升级。

实例保存固定：简单/高级模式、规范化参考绑定、资源字节、真实入口契约、条件源码与编译器版本。更新生成新实例，不改既有任务。旧快照不静默重写；已保存历史和终态应仍可查看，不支持的新旧协议之间禁止直接执行或回退激活，并给出重新加载升级资源、通过服务页保存新实例的说明。P1 必须先确认旧快照加载位置，使不支持的执行协议不会导致整个数据库启动或历史列表失败；不引入旧执行器，不重放外部操作。在途任务仍按其已固定内容执行。

编辑器保持主数据自动连线，默认折叠高级设置；展示自动参考来源和契约。高级设置按资源参考槽位显示来源列表、顺序和错误；移动、删除节点后重新检查依赖。if、while 均在条件位置选择 Python 通用块，展示主输入、参考与 bool 出口，不增加 Python 文本执行框。

- 执行：flow-5 固定协议；每个任务图的状态保存校验后的主输入副本和输出，分支出口收敛、循环逐轮从外层状态创建子作用域。消费者入口预检只将 primary 字段错误归因到直接生产者；参考和模型级跨字段校验立即失败。条件执行独立记录路径并复用取消/预算边界。
