## 1. 业务目标

用户提供部分关于黑神话的 DOCX 文档作为知识库，并提出：

> 我想要基于关于黑神话的三道题目，一道选择题、一道判断题、一道论述题。

服务应理解主题、题型和数量，从所选知识库提取证据，返回三道有依据的题目、答案/评分点、逐题来源以及质量结论。资料不足时明确说明缺项；不能利用模型未提供依据的常识凑题，不能用空题目列表冒充成功。

“黑神话”具体涵盖游戏设定、剧情、制作背景或其他材料，以实际导入文档和请求为准；不在未读文档前编造知识点及标准答案。

## 2. 对现有出题资源的调整

现有[出题契约](../examples/document-question-generation/quality_contracts.py)固定论述、单选、填空三题及固定 ID，引用只包含单文档行号。新实验需要独立版本的请求、计划、题目和审题契约，支持单选、判断、论述及多文档证据；不能仅改 Prompt，也不覆盖已保存的全文出题实例。

建议新增业务交付目录 `examples/black-myth-rag-question-generation/`，实现阶段创建。存放业务契约、Prompt 包、通用块与操作手册；通用读取/检索资源使用前置计划交付的资源。用户文档默认导入平台存储，不自动提交原始 DOCX；未经授权不提交真实模型完整输入输出。`samples/` 继续只维护三类开发模板。

## 3. 输入、输出与业务结论

输入：用户自然语言要求，以及通过页面明确选择的知识库引用。任务提交固定知识库修订；自然语言不能改变检索权限范围或生成执行配置。

解析包输出主题及题目要求数组，规范化块展开为三个稳定题目 ID 的请求项。首版至少严格支持以下组合；其他组合不得静默替换题型或数量，按声明范围返回不支持的请求结论。

| 题型 | 数量 | 必要输出与检查 |
| --- | --- | --- |
| 单选 `single_choice` | 1 | 题干、互不重复的四个选项、唯一答案、解析、依据；人工/审题包检查是否确实唯一 |
| 判断 `true_false` | 1 | 明确命题、严格布尔答案、解释、依据；错误命题给出有依据的纠正，不能把“未提及”判为错误 |
| 论述 `essay` | 1 | 题干、参考答案、可操作评分点、依据；检查能否从资料支持作答和评分 |

业务输出采用明确可校验的结果分支；正式类型由单一契约生成，不以散落的字典约定替代：

- `completed`：准确三题、指定题型分布、答案与证据齐全、审题通过；整体考点不过度重复。
- `insufficient_source`：本次检索证据不足，列出未满足的题目要求、原因、检索范围和受限情况；不宣称整个知识库绝对不存在答案。
- `unsupported_request`：请求超出首版已声明题型/数量等范围，解释支持范围。
- `quality_not_met`：有限修订耗尽后仍存在阻断问题，保留原因与审查记录，不宣称合格题目已交付。

这些是业务结果，不等于平台任务状态。业务结论通过服务输出契约时，平台任务可为 `completed`，页面必须展示业务状态并区分“任务执行成功”和“生成合格题目”。传输失败、无效契约、文件损坏等技术错误仍使任务 `failed`；不转换成资料不足。服务消费者需检查业务状态。

## 4. 固定服务流程

```text
自然语言请求＋知识库引用
  → 需求解析包
  → 规范化和支持范围校验块
  → switch：支持 / 不支持
      支持：读取与检索 → 证据充分性评估与整体三题规划
        → switch：资料充足 / 资料不足
            资料充足：foreach 题目请求项
              → 准备当前题目的证据和输入
              → switch：单选 / 判断 / 论述
              → 对应生成包及统一题目封装块
              → 单题结构与引用核验块
            → 汇总三题并检查请求覆盖
            → 整体审题包
            → 有最大轮数的审题/修订循环
            → 最终结论块
            资料不足：不足结论块
      不支持：不支持结论块
```

1. 首版可先统一检索和规划再逐题生成，避免每题盲目重复扫描；证据按题目请求组织，完整计划和证据集通过 references 传递。
2. foreach 明确选择规范化请求数组，长度为 3，最大条数按该实验范围设定；每项只产生一个统一题目结果。不同题型通过业务联合契约或显式共同封装满足容器契约，并验证兼容检查器实际支持。
3. switch 路由块返回预定义枚举，业务包只生成数据；路由结果不取代原始主数据。
4. 外层整体审题检查跨题重复、题型数量、依据和答案合理性。修订最多两轮；`pass / revise / regenerate / insufficient_source` 用 switch 表达，修订与重出都消耗同一轮数上限。新题必须重新核验和审查。
5. 生成、修订和重出始终限定在本次固定知识库修订与登记证据内。首版不在模型调用后暗中更换知识库或无限扩大检索范围。
6. 输出分支统一成服务结果契约；不同状态需要的字段由联合/关系校验明确约束，不能以可空字段随意组合制造成功。

流程通过正式服务页拼图保存；不新增手写实例入口，不保留自动导入、绑模型及组装服务的脚本。是否复用叶子服务按一层固定版本服务组合限制决定，不因本实验扩展服务嵌套层数。

## 6. 实验矩阵与架构验证

| 场景 | 要验证的结论 |
| --- | --- |
| 正常请求、相关文档 | 正好三题、各题型一题；每题答案和引用经人工核对 |
| 主题相关但内容不足 | 返回具体不足，不编造缺失证据或强行生成论述题 |
| 空知识库、无匹配片段 | 明确业务不足，与文件读取/模型传输失败分开 |
| 混入无关文档 | 选用证据与主题相关，记录检索和上下文范围 |
| 文档中存在冲突表述 | 识别歧义，选择可明确限定来源的考点或报告不足 |
| 判断题为 false | 引用能证明命题错误，纠正说明成立，非“没有提到”推断 |
| 题型重复、漏题、错误引用 | 确定性核验阻止不合格输出；可修订范围内修订，否则明确失败/未达标 |
| 修订与重新生成 | 路由命中正确，轮数有界；未经真实触发的路径记未验证 |
| 替换读取/检索块 | 不修改平台核心，仅换普通资源/显式转换并保存新实例即可运行 |
| 更新或移除知识库文档 | 新任务使用新修订；历史任务仍能展示原证据 |
| 重启与取消 | 服务、知识库和历史恢复；中断任务不续跑，取消遵守既有规则 |

记录材料版本、服务实例、资源版本、模型环境标识（不含凭据）、任务 ID、检索证据、题目、审题意见、实际 loop/token、耗时与人工结论。不要把模型自评作为人工验收，不把结构有效等同于答案正确，不把历史全文出题的 10 次调用当成本实验结果。

本实验完成标准是：真实资料上的主路径可用，必要边界有记录，foreach 和枚举分支确实执行，用户能替换读取/检索实现，文档更新不破坏任务追溯。未触发分支与质量限制明确保留。临时测试、数据及组装脚本在完成时删除；交付资源、操作手册和授权范围内的验收记录保留。
